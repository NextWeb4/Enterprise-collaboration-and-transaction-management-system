# 首个交付范围与开发顺序

> 文档状态：Draft for Review  
> 版本：0.2.0  
> 日期：2026-10-31  
> 说明：本文不是“产品功能上限”，而是第一阶段之后的开发顺序与首个可验收版本（R1）。原有 P0/P1 功能全部保留；不做事先缩减范围的人为最小闭环拆分。  
> 关联：[产品需求](product-requirements.md)、[路线图](../04-development/development-roadmap.md)、[验收标准](../04-development/acceptance-criteria.md)

## 1. 结论

- **单组织部署**；无多租户、无组织切换、无跨组织隔离。
- **无 SQL/ORM/独立数据库服务/Docker**；LMDB + 本地文件。
- **R1 = P0 核心 + 完整文档中心核心能力**（原文档中心五项），因为原验收标准要求文档闭环；这不是缩减后的 人为最小闭环，而是完整模块。
- **P1 = 日程、统计、文档增强等**，保留完整规划，按后续版本交付。
- 开发顺序按依赖排序；不把“后做”写成“不做”。

## 2. 范围原则

1. 保留原产品全部模块：工作台、项目、任务、OA、组织、系统、文档、日程、统计。
2. 不删除原有有效需求；不为降低工作量把模块改成演示版。
3. 文档中心按完整范围设计：文件管理、分类标签、搜索、权限、版本；不做 人为最小闭环 命名与范围切割。
4. R1/P1 是交付顺序，不是产品能力边界。
5. 新增/变更需求必须走变更控制，等量交换或延期，不静默扩张。

| 模块 | 纳入内容 | 切片 |
|---|---|---|

| 工作台 | 我的待办、待我审批、通知、最近项目、工作概览 | M2 |

| OA | 五类申请、顺序审批、模板版本、历史、撤回、转交 | M2 |
| 组织 | 组织架构、部门、员工、岗位、角色、权限 | M3 |
| 系统 | 用户、角色分配、登录记录、操作日志、系统配置 | M3 |

## 4. R1 不纳入（后续版本）

| 模块/能力 | 说明 |
|---|---|
| 日程/会议/提醒 | P1 完整规划，R1 后交付 |
| 数据报表/导出 | P1 完整规划 |
| 文档在线预览/版本恢复/全文检索 | P2 增强，不属于 R1；不影响文档中心核心完整性 |
| 会签/或签/条件分支/委托 | P1/P2 评估，不缩小现有顺序审批 |
| 邮件/企业 IM/SSO | P1 集成 |
| 移动原生 App/Electron | 不在计划 |
| 多组织/外部访客 | 不在单组织边界内 |
| 自定义字段/任务状态/看板列 | 不在当前范围 |

> “R1 不纳入”不等于删除需求；所有 P1 功能仍在产品路线图中。

## 5. 开发切片

### M0：基础、身份、存储（3 周）

- 单机 Node/Fastify、前端壳、单端口静态托管。
- LMDB StorageEngine、Repository/UnitOfWork、索引注册、SchemaRegistry。
- 用户/会话/角色/权限/审计框架。
- 数据目录、单实例锁、健康检查、日志、初始化向导。
- 存储崩溃/索引重建基础脚本。

**退出**：登录闭环；事务/索引/崩溃原型集成测试；无 SQL/Docker。

### M1：项目与任务（3 周）

- 项目/成员/状态、任务/编号/看板/进度/评论。
- LMDB 索引与唯一约束；项目序号事务。
- 工作台项目部分。

**退出**：项目闭环 E2E；并发任务编号；看板并发。

### M2：OA 与工作台（3 周）

- 五类申请、模板/版本、实例/步骤、审批记录/哈希链。
- 审批通过/驳回/撤回/转交；通知；工作台审批。
- 附件文件协议。

**退出**：OA 闭环 E2E；并发审批；文件一致性。

### M3：组织、系统、文档（4 周）

- 组织/部门/员工/岗位/角色/权限。
- 用户/登录/审计/配置。
- 完整文档中心核心：上传/分类/标签/ACL/搜索/版本。
- 文档 ACL 与项目继承。

**退出**：权限矩阵；文档闭环；IDOR。

### M4：硬化、部署、试点（3 周）

- 崩溃/断电/索引重建演练。
- 安全、性能、并发、移动端。
- 普通进程/默认本机 HTTP；局域网显式开放。
- 试点反馈与缺陷修复。

**退出**：验收标准全部通过；无 P0/P1 缺陷。

总计约 **16 周**（单人 + AI 辅助，含缓冲），范围变更需重估。

## 6. 与旧版的差异

| 旧版 | 新版 |
|---|---|
| PostgreSQL + Prisma | LMDB + JSON 文档 + Repository |
| Docker Compose | Windows 本机 Node + 静态 SPA |
| 多组织预留 `organization_id` | 单组织，删除该字段 |
| 人为最小闭环 | 完整文档中心核心进入 R1；不做人为拆分 |
| SQL 迁移 | schemaVersion + 停机分块迁移/索引重建 |
| 真实数据库测试 | LMDB 临时目录 + 崩溃/并发测试 |

## 7. 依赖顺序

```text
M0 存储/身份/权限/审计
  ├─→ M1 项目/任务
  ├─→ M2 OA/工作台
  └─→ M3 组织/系统/文档
        └─→ M4 验收/部署
```

存储层必须先于业务模块完成；禁止业务模块先写 JSON 文件、后补 Repository。

## 8. 验收口径

详细见 [验收标准](../04-development/acceptance-criteria.md)：

1. 项目闭环。
2. OA 闭环。
3. 权限闭环。
4. 文档闭环（完整核心能力）。
5. 存储：事务/崩溃/索引重建。
6. 部署：Windows 本机、局域网、无 Docker/DB 服务。
7. 安全：CSRF/IDOR/上传/审计。
8. 无 P0/P1 缺陷。

## 9. 范围变更规则

1. 写变更说明（价值/验收/影响）。
2. 估算。
3. 等量移除或延期。
4. 更新 PRD/故事/路线图/验收/决策记录。
5. 人工确认后实施。

不接受“先做演示版，后面再补完整功能”。
