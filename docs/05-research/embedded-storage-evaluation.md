# 嵌入式存储方案研究与原型验证

> 文档状态：Draft for Review  
> 版本：0.1.0  
> 日期：2026-10-31  
> 验证性质：独立临时目录原型，不是正式项目依赖  
> 结论：**确定 LMDB（`lmdb` 3.5.9）；ClassicLevel 不采用。正式项目依赖尚未安装。**  
> **重要**：本文是历史原型记录；不包含产品备份设计。最新决策明确 R1 不建设备份系统。

## 1. 目标与边界

本项目要求：

- 单组织部署；
- 不依赖独立数据库服务；
- 不使用 SQL 数据库及 SQL ORM；
- Windows 本机优先；
- 数据保存在本机文件；
- 支持事务/原子写入、并发、崩溃恢复、索引重建；
- 不能把所有业务数据放在单个 JSON 文件里；
- 审批/审计历史不可覆盖。

本验证只回答“存储引擎能否满足这些要求”，不开发正式业务模块，不把原型代码放入项目目录。

## 4. 验证方法

### 4.1 LMDB 用例

1. 创建 users/tasks/audit/index/counter 等命名子库。
2. 创建用户：用户文档 + 邮箱唯一索引 + 审计记录，同一同步事务。
3. 重复邮箱：事务内检查索引，抛出错误，验证用户/索引/审计均未写入。
4. 故意回滚：更新用户 + 写索引 + 写审计后抛错，验证三者都回滚。
5. 100 个并发事务对计数器做“读-加一-写”，验证最终值 100。
6. 2000 个任务写入 + 项目/状态/排序复合索引；范围查询验证 666 条 done；索引重建后数量一致。
9. 异常退出：子进程持续写“任务 + 审计 + 计数器”事务，1.2 秒后 `taskkill /F`；重启后验证计数一致。
10. 两进程并发写：两个 Node 进程各写 300 个事务，验证总数/计数器 600。
11. 数据损坏：复制数据库目录并截断 `data.mdb` 8KB，尝试读取；记录错误。
12. 50,000 任务性能：批量写入、索引范围查询、1000 次按 ID 读取、RSS、实际文件大小。

### 4.2 ClassicLevel 用例

1. 基本 CRUD + 应用层唯一索引。
2. 原子 batch 写用户 + 索引。
3. 100 个并发“读-改-写”计数器（读后 `setImmediate` 再 batch），验证丢失更新。
4. 20,000 任务 + 复合索引；范围查询 2000 条；1000 次读取。
5. 关闭后复制目录，重新打开验证。
6. 异常退出恢复：子进程持续 batch 写“任务 + 审计 + 计数器”，强杀后重启验证一致性。

## 5. 验证结果

### 5.1 功能与一致性

| 能力 | LMDB | ClassicLevel |
|---|---|---|
| CRUD | ✅ | ✅ |
| 应用层唯一索引 | ✅ | ✅ |
| 多记录原子事务 | ✅ | ✅（batch） |
| 事务内读-改-写原子性 | ✅ | ❌（需单写队列；100 并发只保留 1） |
| 多进程并发写 | ✅ 2 进程 600/600 | ❌ 独占锁（README 明确） |
| 异常退出恢复 | ✅ 4146/4146/4146 一致 | ✅ 16375/16375/16375 一致 |
| 索引重建 | ✅ | 可遍历重建（未计时） |
| 数据损坏检测 | 读取报 `MDB_CORRUPTED`；无内置 repair | 有 `repair()`，可能丢数据（未测） |
| TypeScript 声明 | ✅ `index.d.ts` | ✅ `index.d.ts` |
| Windows 预编译 | ✅ `@lmdb/lmdb-win32-x64` | ✅ 预编译 |
| 维护活跃度 | 2026-10 更新 | 2025-04 更新 |

**关键结论**：ClassicLevel 的 batch 是原子“写批”，不是“事务内读-改-写”。在 100 个并发计数器测试中最终值为 1，丢失 99 次更新。要安全使用必须引入应用级单写队列/锁，且无法多进程写入；这对审批状态、任务编号、审计序号等关键写路径不够稳妥。

### 5.2 性能（本机原型）

| 指标 | LMDB | ClassicLevel |
|---|---:|---:|
| 写入量 | 50,000 任务 | 20,000 任务 |
| 写入方式 | 每 500 条一个同步事务 | 每 500 条一个 batch |
| 总写入耗时 | 1,457 ms | 130 ms |
| 写入吞吐 | 34,312 条/s | 153,961 条/s |
| 索引范围查询 | 5,000 条：7.84 ms | 2,000 条：8.49 ms |
| 按 ID 读取 1000 条 | 3.89 ms | 25.97 ms |
| 进程 RSS | 65 MB | 未记录 |
| 数据库实际大小 | `data.mdb` 25.7 MB | 未完整统计 |

说明：

- 不是严格基准：数据量不同（50k vs 20k）、索引键不同、ClassicLevel 写入 batch 更大；只能作为数量级参考。
- LMDB 插入较慢但读取明显更快，且提供真正的事务读改写；本项目读多写少，审批/任务写入正确性优先。
- LMDB 的 `mapSize` 是虚拟地址空间预留，不等于磁盘占用；测试数据 50k 任务只占约 25.7MB `data.mdb`。
- 65MB RSS 包含 Node 进程与 LMDB 映射，未做长时间稳定性/内存泄漏测试。

### 5.3 数据损坏

- 截断 LMDB `data.mdb` 8KB 后，打开不一定立即失败；读取时返回 `MDB_CORRUPTED: Located page was wrong type`。
- LMDB 没有应用层“修复损坏页”的 API；R1 不建设备份系统，不提供自动恢复。
- 不能把“LMDB 是 ACID”理解为“磁盘/文件被篡改也能自动修复”。需要数据目录 ACL、磁盘健康监控、业务层校验（文件 SHA-256、审计哈希链）。
- Windows Defender/杀毒软件可能锁定/扫描 `data.mdb`，需评估排除数据目录或接受性能影响；这是安全与性能的权衡，不能默认关闭。

### 5.4 文件一致性原型

- 文件写入临时文件 → fsync → 按 SHA-256 命名 → 原子 rename → 同一 LMDB 事务写文件元数据/文档。
- 模拟数据库事务失败：删除无引用的最终文件，物理文件数/元数据数一致。
- 结论：文件与 KV 无法共享一个事务，必须采用“先写文件、后写元数据、失败补偿、启动 orphan 扫描”的协议。
- 不提供文件/元数据备份；仅做校验与对账。

## 6. 结论与推荐

### 6.1 推荐

**首选：LMDB（`lmdb` 3.5.9）**，原因：

1. 真正的 ACID 事务，支持事务内读-改-写；适合审批状态、任务编号、审计序号。
2. 单写多读 + 多进程读写的成熟模型；崩溃恢复测试通过。
3. 单写多读、崩溃恢复、索引重建能力满足要求。
4. Windows 预编译、Node 24 加载成功、TypeScript 声明齐全。
5. 读取性能好，50k 任务原型仅约 25.7MB 数据、65MB RSS。
6. 维护活跃（2026-10 仍有发布）。

**备选：ClassicLevel**，仅当 LMDB 在目标环境出现无法解决的 native/许可证问题时考虑；必须：

- 应用层单写队列；
- 所有读改写串行化；
- 接受无法多进程写入；
- 重新验证事务/并发。

**不推荐**：NeDB（多文档事务弱）、lowdb（单 JSON 文件）、自研 JSON 日志（恢复/索引/并发成本高）。

### 6.2 不选 LMDB 的触发条件

- 目标环境无法加载 `@lmdb/lmdb-win32-x64` 且无法编译；
- 需要跨网络文件系统（LMDB 不适合 SMB/NFS 共享数据目录）；
- 需要多主写入/分布式部署（本项目单机单进程，不适用）；
- 需要内置页级校验/自动修复（LMDB 不提供）。

## 8. 正式项目接入建议

1. 正式依赖：`lmdb` 固定版本，保留 `pnpm-lock.yaml`；确认 Windows 预编译与 Node 24 ABI。
2. 打开选项：`encoding: 'json'`（可读、可迁移）、`maxDbs: 128`、`mapSize: 2–4GB`（虚拟预留，按容量调整）、`overlappingSync` 在 Windows 保持默认关闭。
3. 所有写操作通过 `StorageRepository`/`UnitOfWork`，禁止业务模块直接 `open()` 或访问 `data.mdb`。
4. 每个实体一个命名 DB；索引单独命名 DB；索引可重建。
5. 关键写路径使用 `env.transaction(async () => { ... })` 或 `transactionSync`；禁止跨事务多步写。
7. 数据目录放在本地盘，不放在 SMB/NFS/OneDrive 同步目录。
8. 正式报告记录版本、配置、测试结果；不把本原型的数字当成生产 SLA。
